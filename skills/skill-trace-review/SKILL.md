# skill-trace-review：照调用 trace 改 skill

每次调用都会把 SKILL.md 全文读进上下文，有的 skill 循环里每轮都读一遍。判断一句话有没有用，看 trace：模型照它做了什么，user 对结果说了什么。不看它读起来像不像有用。

产出是改好的 skill，外加一份报告。每周跑一轮（user 2026-11-25「应该每周分析一次，更新skill」）。定时任务是 `scripts/weekly.py`：它挑一台有余量的主机开卡，卡里跑本 skill。

`<run>` 指本 skill 所在仓库根下的 `.humanize/skill-trace/<YYYY-MM-DD>/`，不入库。定时任务已经建好了这个目录，手动跑就自己建。上一轮的目录在它旁边。

## 1. 挑 skill，抽 trace

```bash
python3 <本 skill>/scripts/extract.py <run> --list       # 近 7 天调用过的 skill：次数、正文字节、次数×字节、路径 → <run>/skills.tsv
python3 <本 skill>/scripts/extract.py <run> <skill> ...  # 每个 skill 最近 60 次调用的 trace → <run>/<skill>.txt
```

挑哪些：
- 只挑路径落在我们能提交的仓库里的 skill。插件缓存里别人的 skill 和内置 skill 不审。
- 按「次数×字节」从大到小挑。
- 再加上上一轮报告里「下一轮该看到什么」还没核过的 skill。
- user 点了名的，照点名挑。

一轮最多派 10 个审稿 agent，小 skill 两三个合给一个 agent。

脚本只读 Claude Code 的会话记录。由 Codex 跑的 skill（比如钩子起的旁观者）要直接读各机 `~/.codex/sessions/` 里的 rollout：一个 tick 算一次调用，数它每个 tick 把正文读了几遍。还要查 `~/.codex/skills/<skill>` 是不是一份和正本内容不同的独立副本。

## 2. 先读上一轮

读上一轮的 `report.md`：
- 改过的每一条都写了「下一轮 trace 该看到什么」。这一轮照着核，没看到就说明没改对，把那条重开。
- user 驳回过的不再提；user 定了的照做。

## 3. 派审

每个 skill（或一组小 skill）派一个只读的 general-purpose agent，在一条消息里并行派出，后台跑。派单就是 `references/brief.md` 的全文，填上 skill 名、正文路径、trace 文件，以及上一轮关于它的条目。

## 4. 核

agent 报的行号和计数常有偏差。要改的每一条，动手前当场核三件事：
- 那一行的原文还在，而且就是它说的那句；
- 它引的调用 #k，trace 里确实是那样；
- 说「重复」的，另一处确实写着同一条规则。

核不过的丢掉。别的会话正在改的文件（`git status` 显示有改动，或 mtime 在几分钟内）这一轮不改，记进报告。

## 5. 改

**核过、把握高的直接改：**
- brief 里五类多余的话（1–5）。重复的只留一处正本，其余删掉或换成一句指针。
- 没管用的规则，改成能照做的写法：缺数值的补上数值，和 user 裁定冲突的照裁定改，写错的路径改对。
- 模型每次都现推的答案（每次读源码才拼出来的命令、每次重写的小脚本），把答案写进 skill，或者做成 skill 目录里的脚本。
- 很少用到的整节挪进 `references/`。正文只留触发条件和一句指针，每次调用都能少读这些字。
- 让 skill 被反复整篇重读的指示（循环里每轮重读、slash 形式每轮重新注入），改成只在文件变了或上下文压缩之后才重读。

**只列不改，交给 user：**
- user 裁定本身（带「user 日期「原话」」的规则），没被触发也不删。裁定后面附的原话和日期这类装饰算一整类，报出字节数让 user 定。
- 把握中、低的。
- 两条路各有代价的取舍。
- fork 仓库里属于上游的段落。删了之后每次合并上游都会冲突。

**改法：**
- 写替换后的原文，不写「建议改进 X」。
- 公开仓库里不写主机名、本机路径、项目里的名字（提交钩子会查）。
- 有镜像副本的一起改，比如给 Codex 用的 `skills-codex/`、fork 的 fork-local 清单。
- 按仓库分别提交，只带自己改的路径，提交信息里每条写上证据。
- 推送照各仓库的规矩；没有规矩就等 user。

## 6. 报告

写 `<run>/report.md`，每个 skill 一节：
- 正文字节，改前 → 改后；
- 改了的每一条：改了什么、证据、下一轮 trace 该看到什么；
- 没改的每一条：为什么没改（等 user、太新、核不过、别人在改）。

user 之后的答复，以及照答复做的改动，追加在报告后面，下一轮会读。

收尾消息：
- 每个 skill 一行：删了多少字节，最要紧的一处改动是什么。
- 有要 user 定的，最后单起一行，以 `【等 user 定】` 开头，把问题编号写全。
