# 审一个 skill：照它的调用 trace，判断正文里哪些话多余、哪些规则要改

只读：不改任何文件，不提交，只交一份报告。

## 材料

- 正文：{SKILL_PATH}，加上调用时会读到的参考文件（正文里点名的 `references/*.md`、共享参考页）。每次调用都会读进上下文，所以每一行都有 token 成本。
- trace：{TRACE_FILE}。
  - 每段 `======== #k` 是一次调用，新的在前。`INVOKED` 是怎么调起来的，`REQUEST` 是调用前 user 说的话。
  - 后面是会话接着做了什么：`A:` 模型说的话，`T:` 工具调用，`R:` 工具结果摘要，`HUMAN:` user 的下一句。user 的纠正、抱怨、追问是最强的信号。
  - `========` 那一行带原始 jsonl 的路径，要看细节就去读原文件。
  - 先通读最新的 8–10 次，其余的按需 grep。
  - Codex 跑的 skill 另有 `<skill>.codex.txt`，每段第二行是 rollout 路径。rollout 里 `event_msg` 的 `task_started` 开一个 tick，`response_item` 的 `custom_tool_call`（`input` 是跑的命令）和 `custom_tool_call_output` 是工具调用和结果，`message`（role=assistant）是模型说的话，`compacted` 是压缩。
- 上一轮关于这个 skill 的报告条目：{PREVIOUS}。没有就是第一次审。
- 查一句话是哪天加的：`git -C <仓库> log -L <起>,<止>:<相对路径> --format='%cs %s' -s | head`，或者用 `git blame`。比最新一次调用还新的句子，trace 判不了，标「太新」。

## 找两种东西

**多余的话**，归到下面五类之一：

1. 从没起作用：所有调用里模型都没照它做过，也没有哪次因为缺了它而出错；它要防的情形从没出现过。
2. 重复：本 skill 别处、另一个 skill、项目规则或 memory 里已经写过（两处位置都给出来）。
3. 过程叙事：规则的来历、事故经过、「之前 X 现在 Y」、日期流水。规则本身留下，故事删掉。
4. 模型本来就会做：不读这句，模型也一直这么做。
5. 反而造成浪费：照它做白费了工夫，或者 user 对照它做出的结果不满意。

**要改的**：

- 没管用的规则：一再被违反，或者照做了也没防住它要防的事。
- 冲突：和 user 的裁定、项目规则、别的 skill 说法相反（两处都给出来）。
- 模型每次都要现推的：每次调用都去读源码拼命令、重写同一个小脚本、去别处查正文没写的规则。数出发生了几次。
- user 在调用之后的第一句话就是追问（「怎么改」「为啥」）：多半是报告格式缺了东西。
- 成本：每次调用读进多少字节、被重读几遍（循环里每轮都重读、slash 形式每轮重新注入），哪一段最贵。

注意：

- 带 user 裁定的规则（「user 日期「原话」」）没被触发，不算无用。单列成「user 裁定、未触发」，不提议删。裁定后面附的原话和日期作为一整类处理，报出共占多少字节。
- 指出具体句子：引原文，给 `文件:行号`。不写「这节太长」这种话。
- 每条都要有证据（调用编号 #k、计数）。没有证据的，标「仅读正文判断」。
- 起了作用的段落也要记下来（照它做避免了出错、user 认可了结果），清理时防止误删。

## 报告（中文，先给结论）

1. 一句话：能删多少（行数、字节），最该删和最该改的分别是哪几处。
2. 删除候选：`行号 | 原文摘要（≤40 字）| 类别 | 证据 | 把握（高/中/低）`，先按把握、再按体量排。
3. 要改的：`行号 | 问题 | 证据 | 建议的替换原文 | 把握`。
4. 保留清单：起了作用的段落，每段一句证据。
5. 上一轮的条目核下来怎样（如果有上一轮）。
6. 读了哪些调用，哪些没读。
