# 文档术语盲读审查(盲读 → 查证 → 改写)

## 核心原则

**顺序不可颠倒。** 先盲读、后看仓库。看过代码之后你就再也看不见术语了——每个自造词都会自动被脑补成"显然的意思",这正是原作者当初写出这些词的原因。第一趟的唯一目的是保留"看不懂"这个信号,它一次性、不可再生。

**盲读的困惑必须落盘。** 第二趟要读代码,读完记忆就被污染了,记不住自己当初卡在哪。

## 第一趟:逐个盲读

先 `ls <目标目录>/*.md` 列清单,建 ledger 目录,然后一个一个来。读第 N 个文件时:

- 只 Read 这一个 md。**不读**别的 md、不读 README、不读代码、不 grep、不看 git log。
- 允许的例外只有"文件系统管道":列清单的 `ls`、建目录的 `mkdir`、写 ledger。**禁的是读任何其他文件的内容**,不是禁一切命令。
- 装成第一次进这个项目的同行:懂这个领域,但没读过这个仓库、没读过配套的 plan 页和前几轮结果页。
- **定义晚于使用,算问题。** 读到第 60 行才补上的定义,救不了第 12 行那个已经被卡住的读者。这类照记,但**处置不是换词,是把定义搬到首次出现处**——所以 ledger 的 `首次出现` 行必须准。

> 隔离提醒:如果本次会话已经读过这个仓库的代码,你已经污染了,盲读结果不可信。此时把每个文件派给一个独立 subagent 去盲读(每个 agent 只给一个文件路径、禁止它读其他文件),每个 agent 交一份 ledger,你只做汇总不做补充。

### 记什么:门槛

**门槛是"必须停下重读这句话,或必须前后翻页才能继续"。** 能带着一个临时含义按正常速度读下去、且后文没有推翻它的,不记。

不要把"每个没见过的名词"都记进去——那等于什么都没标。生僻但不卡壳的口语词(`买`打底、`释`卡)放过;**含义会漂移的词必须记**(同一个词第三次出现时你又得重猜 = 记)。

**量的校准:** 承重条目通常 5–15 条。若"承重"超过 20 条,说明这不是措辞问题而是结构问题——**停止逐词记录,直接写文档级判定**(见下)。

### 类型

**A 组 · 换词能修的**

- **自造词**——像术语,但这个领域没这个说法。含一个高频子类:**概念是领域标准的,但中文写法是自造的**(如"亚随机"↔ 通行写法"低于随机水平 / below chance")——这类最容易被漏,因为它读起来像个正经术语。
- **缩写 / 记号无图例**——首次出现即缩写或符号,全文不展开;或**定义晚于使用**(标题、摘要里用了正文才定义的记号)。
- **悬空指代**——"那个 gate""五互斥终局""第三层":哪个?哪五个?哪三层?
- **名不副实**——名字暗示 A,实际是 B。含字段名与紧跟其后的注释互相打脸的情况。
- **同物异名 / 一词多义**——同一篇里两个词指一个东西,或一个词指两个东西。

**B 组 · 换词修不了的**(盲读者比任何人都容易发现,因为你没有先验去替它圆场)

- **隐含前提**——句子通顺,但要先知道某个没写出来的外部事实才成立。
- **断句歧义**——中英混排、缺标点导致两种读法含义相反("无 NARROW、无关证据动作")。
- **自相矛盾**——摘要断言 A,正文撤回 A;同页两处数字/结论打架。**这是文档 bug,不需要看代码就能判,单独报,不许靠改措辞抹平。**
- **数目不自洽**——号称"四源"实际是 3×2 六格;同一份数据两处给不同条数;并列项报数规则不一致。
- **一句话塞太多**——单个术语都没问题,但一句里堆了十几个专名,任何速度都读不动。处置是拆成列表,不是换词。

### ledger 格式

写到 `.humanize/jargon/<UTC时间戳>/ledger-<文件名>.md`,**一个源文件一份 ledger**(subagent 并行时天然不冲突;汇总时也不必合并)。

用分块、不用表格——`卡点`和`我猜是`是长句,表格会把它们压成一行。每条:

```
### N. <一句话标题>
- 首次出现:file.md:12          ← 第二趟按这行插定义,必须准
- 其它出现::31 :44 :88         ← 只列让理解更糟的那几处,不用穷举
- 原句:<逐字抄,别转述>
- 类型:自造词
- 卡点:<为什么读不下去,一句话>
- 我猜是:<你的猜测>  置信度:sure | guess | no idea
- 严重度:承重 | 局部 | 表面
```

两个字段容易记混,分工是:

- **置信度**衡量*你*有多确定——第二趟拿它验证这个词的误导性有多强。
- **严重度**衡量*读者*被伤得多重:**承重**=全文结论挂在它上面(不懂它就整页作废);**局部**=只影响这一节;**表面**=读着别扭但不影响理解。二者独立——一个词可以既 `guess` 又只是 `表面`。

ledger 末尾另开两节:

- **文档级判定**——不锚在任何行号上的整篇问题。最常见的一条:*本页不是独立文档,是对某份 plan 的 diff*(症状:一半的悬空指代都"翻开 plan 十秒就能答")。这类问题的正解是加一个"前置概念"小节,不是逐词改写;不写在这里就只能表现为 30 条零散条目,严重程度被稀释掉。也放:中英混排约定(哪些英文词是代码标识符、哪些只是习惯)、密度问题。
- **良品名单**——你专门判定过"这是真术语,别动"的词(`Holm 校正`、`聚类 bootstrap`、`主终点/次要终点`、`prefill`、`oracle`)。不写下来,这个判断就在两趟之间丢了,第二趟会重新纠结甚至把它们改成大白话。

## 第二趟:查证 + 改写

现在才允许读代码和其他文档。**注意 grep 的是这篇文档所属的那个仓库**——目标文档可能不在当前 cwd 的仓库里。

先按 `严重度` 排序,但**排完先找承重条目之间的共同根因**——它们往往有一半出自同一个病(最常见:全是 plan diff),一节小节能一次干掉六条。逐条处置承重是最浪费的做法。之后表面条目可以整批放过。

**改之前先对账。** `grep -rn 原词` 的命中率比想象中低得多:承重条目里的核心词往往在代码里叫别的名字(「片加权」= `piece_mean`、「打底」= `ADD_GROUND`),grep 原词一次都打不中。有效顺序是:**先把 artifact / 数据文件拉出来,跟文中每个数字逐个对一遍**,再去 grep 词。数值对不上时反解它(某个差值恰好等于 `λ·slt/1e4` → 才找到成本口径的真相)——文档里最严重的错通常是数字错,而数字错只能这样找出来,不可能靠读措辞发现。

**B 组条目不进改写流程**:自相矛盾、数目不自洽 → 直接列给用户(这是 bug);断句歧义、一句话塞太多 → 改结构(加标点/拆列表),不换词;**隐含前提 → 补口径 + 同时报**(它多半不是笔误,而是作者脑子里有一套没写下来的约定,补完还得让作者确认补对了)。

**先看文档级判定**:如果结论是"需要一个前置概念小节",那就先写那一节,写完后一大批悬空指代和缩写条目会自动消解,不用再逐条改。被这一节收编的条目,定义就落在文首,`首次出现` 行号作废——别再回去重复插一遍。

A 组逐条处置:

1. **查 ground truth**:这个词在代码里对应什么?定义在哪?实际行为是什么?(`grep -rn` 原词;找不到任何代码对应 = 强信号,见第 3 条)
2. **判定该不该换**:
   - 领域已有标准叫法 → **换成标准叫法**,首次出现处保留原词一次:`标准词(仓库内旧称 X)`,让老读者能对上。
   - 概念真实存在但领域确实没有现成词 → **保留自造词,在 `首次出现` 那一行加一句定义**,并锚到最近的标准概念("X 指 …,相当于 … 的变体")。
   - **该词描述的事和代码做的事不一致** → 文档 bug,单独报,同上不许靠措辞抹平。
   - 良品名单里的、以及精确的领域术语 → 原样留着。
3. **"领域通用词"从哪来**(按优先级):这个领域公开文献/教材里的叫法 → 依赖库或上游项目的官方命名 → 仓库里已经在用的更通用的同义词。**不要自己发明新词**——发明就是又造了一个只有你懂的词。
4. **改写纪律**:
   - 只动措辞,不动事实、不动数字、不动结论。**界线**:从 plan / 代码 / artifact **搬运**一条已经存在的事实过来当定义 = 允许(前置概念小节整个都是这么写出来的);**推断、补全缺失项、扩大结论范围** = 动事实,禁止。表里少两行、九条只列了八条 → 只报不补,补数就是加事实。
   - 每处改动可回溯到 ledger 的某一条,ledger 上没有的地方不顺手改;
   - 换了词就全文一致换,别留半新半旧;跨文件同词同改;
   - `sure` + `表面` 的可以只记不改(**预期 50%+ 的条目最终判为无需改,这是正常的,不是第一趟记多了**);`承重` 的必须有处置。

## 验收

- 每条 `承重` 和 `局部` 都有处置:换词 / 加定义 / 报为 bug / 判定无需改(写明理由);
- 文档级判定每条都有回应(采纳并改结构 / 说明为何不改);
- **验收盲读是强制步骤,且必须派给独立 subagent**(不是"理想情况"):你在第二趟里已经被代码污染第二次了,自己重读绝对发现不了残留——实测这一步抓到的正是第一趟漏掉的那条承重条目(一个符号从头到尾没定义,盲读者记了、我没记,因为我"默认读者知道")。新一轮不再产生 `承重` 条目才算过;
- 全文没有新增只有本仓库懂的词;
- 汇报分三块,**顺序不能反**:①文档级问题与结构改动 ②发现的 bug(自相矛盾、数目不自洽、文档与实现不符) ③已改的措辞。措辞列表最长但最不重要,放最后。

## 常见错判

| 症状 | 纠正 |
|---|---|
| 边读边 grep 代码"确认一下" | 盲读就作废了;确认放第二趟 |
| 后文有定义就放过 | 定义晚于使用照记,把定义搬到首次出现处 |
| 每个没见过的名词都记 → 上百条 | 门槛是"必须重读或翻页",不是"不眼熟" |
| 承重条目 20+ 还在逐词记 | 那是结构问题,转去写文档级判定 |
| 把术语当 jargon 改成大白话 | 领域读者认得的原样留,进良品名单 |
| 标准概念的自造中文写法被放过 | 这类最隐蔽,按"换成通行写法"处理 |
| 发明一个"更清楚"的新词 | 只能用领域已有的词,否则是新黑话 |
| 摘要与正文打架,顺手改一处对齐 | 这是 bug,先报;信哪个由用户定 |
| "本页读不懂"被摊成 30 条悬空指代 | 写进文档级判定,正解是加前置概念小节 |
| 只改了这次读的文件,别处旧词还在 | 换词要全仓一致 |
