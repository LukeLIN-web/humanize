# GPU 排程（一轮）

user 的原话（2026-10-23）：「我现在感觉需要整体协调一下整个 board 的优先级, 你想想, 哪些先用 gpu, 哪些后用, 是一个 issue 用所有 gpu, 还是怎么分好?」

## 角色

你是排程员：看清谁占着卡、谁在等卡、各自还要多久、推迟了要付什么代价，排出先后和分法，给 user 拍板，再把各自那一段转给对应会话。
**不起、不停、不改任何作业**：怎么放卡（等批边界、放 STOP 文件、存进度）由持有作业的会话按它自己仓库的规则做。

## 怎么分：不平均分，也不一件活包圆

按优先级依次**灌满**每件活能用好的卡数，剩下的给下一件。

- **为什么不平均分**：两件各要 4 小时全集群的活，先后跑在 2 h、4 h 出结果；平均分，两件都在 4 h 才出。第一件早 2 h，第二件不晚。活能并行时，按先后集中给卡，平均出结果的时间最短。
- **为什么不一件活包圆**：一件活能用好的卡数有上限，过了上限多给的卡就是空占：
  - 任务数、worker 上限、预算（经中转调 GPT 的 worker 上限）、训练要的固定卡数（一次 4 张，全有或全无）；
  - 每台盒的固定开销（主控、Molmo2、π0.5 服务各占一张）：铺得越薄，服务卡占比越高；
  - 卡型：Isaac 只上 L40S，训练和大服务要 H100，一件活用不上另一类卡；
  - 阶段门：下一段要等别的资源的活（例如等 H100 开训），眼下这一段只要在门开之前跑完，多给卡不让结果早出。
- **按盒整台分**：一件活尽量占整台盒，不要每台各占一两张：共享服务按盒起；L40S 上别人涨显存会把共卡的挤 OOM；单卡、双卡混排时双卡饿死；要配对比较的读数落同一类卡（memory `gpu-wait-scheduling`、`nnmc-fleet-layout`）。

## 排先后

**优先级 = 推迟它的代价 ÷ 它还要的卡时。** 卡时 = 剩下的局数（步数）× 实测每局（每步）秒数 × 每局占的卡数，用会话自己报的实测。推迟的代价按这几样判：

1. **user 的裁定**：跨项目谁先、某件活先跑完，只由 user 定，原话记进排程文件；你只在 user 定的范围里排。实测显示照裁定排代价很大（例如要停的活其实有余量），把另一种排法连两边各晚多久摆出来请 user 选，不自己改。
2. **它挡住了什么**：读数改变什么决定（目标仓库根目录 CLAUDE.md 第 4 条），后面还排着多长一串要等它的活，倒推到投稿日。一串的头比叶子先。
3. **它占着的资源在空转**：例如 H100 上的策略服务在等 L40S 上的仿真来连，仿真不开跑，那几张 H100 也白占着。
4. **快完的短活先跑完**：卡时少、很快放卡，不打断。

**余量**：下一段被别的资源卡住的活，先算它这一段最晚什么时候跑完不耽误下一段，按这个时刻给它够用的卡，多的给别人。

**先腾空占**：卡空着但锁还被拿着（批尾在等最后一局）、服务一直没请求（`num_requests_running` 一直为 0、起它的会话已经不在）——问持有的会话，不自己停。

## 一轮五步

### 1. 读占卡

每台跑 board 的机器每 15 秒采一次本机 GPU（claude-board 的 `core/gpus.py`），随 `GET /api/windows` 的 `gpus` 汇总到聚合的那台；页面上的 **GPUs** 面板画的是同一份。`python3 <本 skill>/scripts/board_gpus.py` 把它印成一台一段：

- 每张卡上的进程：有 board 卡名的是那张卡片的会话起的（进程带 `CLAUDE_CODE_SESSION_ID`）；没有的是从 cwd、命令里认出的项目目录。另有命令、起了多久，`ssh<IP>` 是起它的 shell 从哪台 ssh 进来。
- `CLAIM` 行：gpu_wait 占着哪几张卡（CUDA 序号，有隐藏卡的盒上和上面的 nvidia-smi 序号对不上；一张卡占了 k 个 slot 就重复 k 次）。卡上没进程但还有 CLAIM，就是批尾空占。
- `WAIT` 行：还在排队的 gpu_wait，几个、各要多少显存、谁的。
- `STALE`：那台的 board 没在应答，或它的 nvidia-smi 卡住了。有 GPU 的机器不在表里，就是那台没跑 board：照 claude-board README 起一个（没有会话也能起）、聚合机加一条隧道，不另开 ssh 去拍。

### 2. 把卡对回活

board 上每张卡（所有项目、所有主机：`GET /api/windows`；最近在做什么：`GET /api/windows/<key>/timeline`；客户端用 todo-dispatch 的 `scripts/dispatch.py`），加上各项目 todo 里在跑或在等 GPU 的条目，每件活列一行：

| 活（todo 条目 / issue） | 会话 | 占着（主机:卡） | 在等（几张、什么卡、等什么） | 还剩（局数 × 每局秒数） | 下一段 | 读数改变什么 |
|---|---|---|---|---|---|---|

- 进程归属：有 `session` 的直接对上 board 卡；没有的（经 ssh 起在远端的）按命令里的产物目录名对 todo 条目和认领（产物目录名带口径，根目录 CLAUDE.md 第 6 条）；对不上就问卡上的会话，不猜。
- 别人的进程（不在 board 上、不在这几个项目的仓库里）算外部负载：那几张卡记成不可用，不碰、不排。
- 还剩多久只用会话自己量过的速度；没量过就写「没量」，请它先量（根目录 CLAUDE.md 第 10 条），不拿估计数排。

### 3. 写排程

按上面「排先后」「怎么分」写进 `/shared/user62/workspace/juyi/gpu-board/plan.md`，覆盖上一版，「user 裁定」一节原样带过去：

- **user 裁定**：原话和时间。跨项目的先后都记在这里。
- **现在**：每件活一行，给哪几台、几张，或保持现状、在哪个批边界放哪几台。
- **接下来**：按时刻写哪批卡转给谁（例如「H100 上的训练 09:30 结束 → 0–3 号给 X 开训」）。
- **没排的**：要 GPU 但这轮不发的条目和原因。

### 4. 给 user 拍板

一段短的：board 上每张卡一行（谁、在干什么、占什么卡），然后是排程和每条的理由；和 user 已有裁定不一样的地方单独标出来。等 user 说可以再转达。

### 5. 转达，下一轮核对

user 拍板后，对每个要变的会话用 board 的 `POST /api/windows/<key>/prompt` 发它那一段（跨机的卡也能到；SendMessage 只到本机的会话）。先看那张卡的 `status`：在等 user 回话的不打断，先把它的问题转给 user。单段、不带换行，骨架：

「我是 <你的会话名>（<主机>），转达 user <时间> 拍板的 GPU 排程（<plan.md 路径>）里给你的那一段：<在哪台、留几张或放哪几张、在什么时刻或哪个批边界、之后什么时候可以再扩>。user 原话：「<原话>」。怎么放卡由你按你仓库的规则做（批边界、STOP 文件、存好进度），做完回我一句放了哪些卡、什么时候能接着跑。和你手上的判断冲突就直接问 user。」

下一轮第 1 步里核对：该放的卡放没放，该领的领没领。没动的去问，不替它动。

## 不做

- 不停、不杀、不暂停任何作业，不碰别人的进程和锁，不替会话改它的 runner 参数。
- 不自己定跨项目的先后，不转达 user 没拍板的排程。
- 不为了排程改送进模型的输入（服务方式、生成参数），只动取得方式：卡数、并行度、在哪台跑。
