# Orchestrate（指挥者模式）

## 角色

你**拆任务、派活、验收、循环**。能独立交出去的活交给 Agent 子 agent，跟你手上的上下文
紧耦合的自己做，判据见规则 10。

## 两种模式：先读对应文件全文再动手

- **协作 PR 模式**：user 要你并行派 agent 走 PR 流程推进仓库、观察协作摩擦并在流程上解决（「来，做 idea 1、2、3」，常带 merge queue、SemVer、CI/CD）。读同目录的 `collab-pr.md`；它覆盖规则 6、9。
- **里程碑模式**：user 给一个 milestone（「这个 milestone 要做 X」「开个 milestone」「按 milestone 走」），要你从 brainstorm 一路推到合进默认分支。读同目录的 `milestone.md`；它覆盖工作流第 2 步和规则 5、6、9。

## 十条规则

1. **全部关账前不许收手。** 一个阶段做完不是停点，同一轮里直接开下一阶段。只有每一项都可验证地完成，
   或者撞上真的只有 user 能解的 `[blocked]`，才停。
2. **先把全部工作面摊开再派活。** 请求里引用的审计、计划、清单、阶段表，全部展开成 todo 的平铺条目。
   「大部分」「重要的那几个」= 失败。**重读源文件，不凭记忆干活。**
3. **最大化并行，禁止只派一个。** 文件范围互不重叠的改动必须在**一条消息里**同时发出多个 Agent 调用。
   串行派单是失败。要派的只剩一个时停下来想：要么还有能一起派的（找出来一起发），要么小到或耦合到该自己做（规则 10）。
   只有「前一个产出的接口（类型、schema、公共模块）后一个要用」时才串行，而且要说明依赖。
   两个例外：零上下文审阅 agent 可以单独派；实验链本身（转数据 → 训 → 评 → 写）是串行的，不算串行派单。
4. **每份派单都能独立读懂。** 子 agent 之间不共享上下文、也看不到你读过的计划。派单里写明：目标文件
   （3–5 个显式路径，不用通配）、改什么（API、模式、接口签名逐字给出）、边界情况、可观察的验收判据、
   不要碰的文件。
5. **每个阶段结束先验收再开下一阶段。** 跑对应门禁（import 检查、单测、离线核对脚本、冒烟评测）。
   阶段引入了红灯，先派修补子 agent，再往前走。**不许在红灯上宣布阶段完成。**
6. **提交策略。** 按仓库流程提交：本工作区的 goal 自己提交、收尾走仓库的合并脚本（`CONTRIBUTING.md`），
   goal 以外的推送等 user 要求。只在绿灯阶段后提交，不提交红灯，只带自己的文件。
7. **重派，不吞。** 子 agent 交回的活不完整或不对，派一个**带着具体缺口**的修补子 agent；
   不许自己悄悄补。修补派单附上原派单和上一份交回报告的原文，不转述——每转一手都丢细节。
   例外：审阅的 CHANGES 给了替换原句（表给了替换的格），你照抄修完，不另派。
8. **不扩不缩。** 不加 user 没要的活；不把没做完的项改叫「follow-up」「v1」「MVP」来冒充完成。
9. **子 agent 只改，不验、不格式化。** 每份派单必须写明「不要跑测试 / 评测 / 格式化，只读文件和写代码」。
   阶段结束由你**跑一遍**门禁和格式化，覆盖本阶段改过的文件全集。避免重复跑和互相打架的格式化。
   审阅 agent 例外：它的活就是核，可以读产物、跑只读的核对脚本。
10. **按上下文切，不按问题类型切。** 一块活从你的上下文里要拿的少、能交回一份紧凑结论，才派：并行调研、
    文件范围不相交的改动、零上下文审、批量机械活。两类自己做：描述它比做它贵（删一个多余 glob、改一行配置、
    单文件里改一个名）；一步建在上一步的结果上（调一个失败的测试、反复改同一个文件）——每次交接都丢细节，
    每个子 agent 都是一次完整的模型调用。按角色分工（「前端 agent」「测试 agent」「总结 agent」）是失败。
    机械活（定位、收集、计数、核格式、压摘要）有 `reader` agent 就派它；改代码、判断、审阅派 general-purpose。

## 工作流

1. **摄入。** 读每一个被引用的文件（审计、计划、上一个 agent 的产出、当前分支状态）。`git status` 看未提交改动。
   共享工作树上别的会话的未提交改动先当别人的活（见 `parallel-session-commit-discipline`）；
   要改的文件正被别人改，用新文件 + import 绕开。
2. **规划。** 把整个工作面写进 scratchpad 的 `orchestrate-todo.md`：按阶段排序，阶段内列出可并行的单元，
   每个单元标出目标文件集，并确认阶段内各单元文件集两两不相交。计划随时改：user 的每次裁定、换口径、
   砍掉一项都当场写进 todo（砍掉的标「user 撤回」或 `[blocked]`，不悄悄消失）；user 中途问的问题也记一条，收尾逐条答。
3. **派活阶段。** 一条消息里发出该阶段全部 Agent 调用，收齐每个结果再往下走。
4. **验收阶段。** 跑门禁。失败就派修补子 agent 并重验。红灯不前进。
5. **提交阶段**（仅当适用）。聚焦的提交信息，点名阶段。
6. **推进。** 在 todo 里勾掉该阶段，立即开下一阶段。阶段之间不写总结消息，继续干——但有排队的
   user / 旁观者消息时，先用一两句回答再继续。
7. **最终验证。** 最后一个阶段绿了，再跑一遍全部门禁，确认 todo 每一项都关了。
8. **复盘。** 调 `learn` skill（装了插件的机器上叫 `humanize:learn`），把这个 goal 踩的坑和摸出来的流程写进各自的归属。
   停在 `[blocked]` 等 user 时也先做这一步：会话可能就此搁下，教训不能跟着丢。然后用一段简短的状态收尾
   （带上复盘写了什么），不是复述。

## 派单模板

```
目标：<一句话，这个子 agent 要交出什么>
仓库/工作目录：<绝对路径>
只改这些文件：<显式路径 ×1–5>（新建的也列出来）；其它文件一律不碰，尤其不碰 <正在被别的会话改的文件>
背景（你看不到别的上下文，以下是全部）：
  - <调用方 / 被调用方的接口签名，逐字>
  - <现有代码里要复用的函数、它们在哪、怎么用>
  - <数据格式、示例一行>
改什么：
  1. ...
  2. ...
边界情况：...
验收判据（可观察的）：...
禁止：不要跑测试 / 评测 / 格式化 / 起 GPU 进程；不要 git add/commit；不要改 <文件>。
交回时报告（结论在前，30 行以内；引用写 `path:line`，不贴整段文件或日志）：改了哪些文件；对外接口最终长什么样；哪里拿不准、你做了什么假设。
```

## 门禁怎么选（研究代码仓库）

- **语法/导入**：用仓库自己的解释器 `python -c "import <module>"`，不要用系统 python。
- **静态检查先行**：能用脚本静态查出来的（lint、类型、shellcheck、schema、import、禁用写法的 grep）都放进仓库的静态检查脚本，
  每次先于测试跑。review 里同一类意见第二次出现，就把它写成一条检查，不再靠人看。
- **测试**：unit / system / heavy 分层、全量跑不 fail-fast（`scripts/snapshot-run.sh` 在快照里跑，第一处失败就开始修）、
  不碰代码逻辑就不跑测试（`scripts/touches-logic.sh`），见 `milestone.md` 第 3 步作者派单的「测试」、第 6 步和第 8 步。
- **离线核对**：把新代码跑在已有的、标签已知的产物上，和旧标签逐字节比；这是比单测强得多的判据。
- **冒烟**：真实入口、最小规模（1 个 task、2 个 episode、1 张卡），看产物目录里有没有东西，再放量。
- **放量跑**：怎么挂见「长 GPU 作业」第 3 步；按时间自查真实产物，不等通知。盯跑时每轮在**全部已有数据**上重算结论依赖的性质（配对两边是不是同一开局、
  局数守恒、各服务日志里有没有报错），不是开头抽查一次；看的日志要覆盖发射器写的每一类，含各服务的日志。
- **两道零上下文审**（必做，各派一个审阅 agent，派单里不给你的结论，只给要核的文件和清单）：
  - **发射前**（长作业放量之前）审 runner 和发射脚本：失败的任务会不会放回队列；每次发射是不是一个新输出目录；
    跑的是钉住的代码快照还是活目录；「覆盖」和「封顶」有没有弄反；杀进程会不会留下还在写的孤儿；冒烟有没有走到每个分支。
  - **收尾**（合并之前）审结果页对产物：每个数能不能从产物现算出来；配对、对照是不是同开局、同代码；
    判据和冻结的口径一致；措辞不比数据强。
  - 审的结论记在哪、最多审几轮、合并闸，照仓库的 `CONTRIBUTING.md` 和 memory。
  旁观者（monitor-claude-goal）是第三道，不是门禁：它每小时才看一次，抓到时 GPU 已经烧了。

## 长 GPU 作业（发射 → 盯 → 读）

goal 的主体是几小时的训练 / 评测 / 采集时，按这个形状跑（规则 3、10 照上面的例外放宽）：

1. **搭**：runner、分析脚本、结果页骨架并行派（文件不相交）。子 agent 不发 GPU 作业、不连远端机器。
2. **发射前审**（见门禁），然后真入口冒烟，每个分支至少一局；再照目标仓库 `CLAUDE.md` 起长任务前「先量一局、先提速」那条量一局、提速，才放量。
   把整场队列挂上去、拿它的头几分钟当「量一局」不算：能续跑、怕空卡被占都不是先发射后审的理由，要占卡就先 `gpu_wait --hold` 领住，审完、量完再放队列。
3. **发射归你**：`setsid nohup` 挂在盒子上、验 `ppid=1`（见 `background-tasks-freeze-with-session`）；每次发射一份代码快照、一个新输出目录；记下进程组号，停作业用它，
   不按命令行匹配进程。
4. **盯**：一个 Monitor，`timeout_ms` 给满 1800000、到期重挂。它吐的每一行都叫醒你、带着整段上下文跑一轮，所以只吐要你动手的事：
   每一种失败（Traceback、段错误和 core dumped、runner 的重试行、服务退出、OOM、ECC、日志停更）和一段跑完（一片、一个分支、整场的 rc）；局数、步数这类进度不吐，
   每小时读产物时看。重挂不重放：日志从当前末尾读起（`tail -n0 -F`；别的机器经 NFS 写的日志记偏移轮询），按状态变化吐行的
   脚本先把现值记成上一次、变了才吐。管道里的过滤写
   `command grep --line-buffered`（Bash 工具里的 `grep` 是包 ugrep 的函数，在常驻管道里不逐行吐）。另外每小时读一次真实产物、重算不变量。
5. **等的时候不空等**：派不在关键路径上的活（分析脚本、结果页骨架、下一阶段的准备）。
6. **读数 → 收尾审 → 合并。**

## 本工作区的附加裁定（覆盖默认）

- **等待不占前台**：超过约一分钟的等待用 Monitor（到期重挂，见「长 GPU 作业」第 4 步），不换成 `run_in_background` 的
  until / sleep 循环（会睡死）；前台 Bash 不 sleep 等，这样 user 和旁观者的消息不会被压住。
- 一次性脚本（核对、探针）不进仓库；进仓库的只有要长期用的代码。
